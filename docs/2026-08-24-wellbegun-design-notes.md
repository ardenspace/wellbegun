# wellbegun — 설계 노트

- 작성일: 2026-08-24
- 상태: 설계 확정, 구현 대기 (새 세션에서 착수 — "다음 세션 시작 가이드" 참조)
- 이름 확정: **wellbegun** — "Well begun is half done"(아리스토텔레스) = "시작이 반이다". 시작할 때 비싼 결정만 제대로 잡아두면 유지보수의 절반은 끝난 것이라는 플러그인의 주장 그 자체. GitHub/npm에서 동명 프로젝트가 발견되지 않음을 확인했다(2026-08-24).

## 한 줄 컨셉

"이 결정을 나중에 바꾸려면 얼마나 드는가?"를 축으로 MVP의 기획 > 스펙 > 플랜 > 런을 이끄는 조합형 스킬 세트. 되돌리기 비싼 결정에만 공을 들이고, 싼 결정은 빠르게 지나가며, 전역 관리 대상(토큰·공통 컴포넌트·공통 계층·스키마)을 처음부터 레지스트리로 묶어 유지보수 비용을 낮춘다.

## 왜 만드는가 (지형 조사 요약)

- 스펙→플랜→런 파이프라인 자체는 포화 상태다: Spec Kit, Superpowers(2026-06 기준 스타 22만+), BMAD, OpenSpec 등. 골격만으로는 차별점이 없다.
- 반면 "결정 가역성 비용"을 기획의 중심 축으로 놓은 스킬/플러그인은 조사에서 발견되지 않았다. 개념 자체는 검증되어 있다(베조스의 one-way/two-way door, InfoQ Architectural Change Cases의 되돌리기 비용 티셔츠 사이즈 추정).
- 전역 관리/하드코딩 드리프트는 제품이 나올 정도로 검증된 고통이다: Buoy(드리프트 감지), DesignDiff(MCP 검증 서버), Factory.ai·Builder.io의 "린터로 에이전트를 통제하라" 계열 글.
- 참고 링크:
  - https://docs.bswen.com/blog/2026-08-07-ai-spec-frameworks-compared/
  - https://www.infoq.com/articles/architectural-change-cases/
  - https://buoy.design/ , https://designdiff.netlify.app/
  - https://factory.ai/news/using-linters-to-direct-agents

## 확정된 결정

### 전략

- 풀 파이프라인(기획>스펙>플랜>런)을 이 플러그인이 소유한다. 다만 런의 안쪽 구현 기술은 Superpowers를 도구함으로 활용한다(필수 의존이 아니라 "있으면 활용").
- Superpowers의 기획/플랜 계열 스킬(brainstorming, writing-plans)은 부르지 않는다. 단계 이중 실행 방지. 런 스킬 본문에 "이 런이 활성일 때는 이 스킬이 지휘자"임을 명시한다.
- 관점 주입은 스킬 트리거와 지시문으로, 반드시 지켜져야 하는 규칙은 훅과 린트로 내려보내는 이중 구조.

### 기획 렌즈 (사용자 관점)

- 기획은 문제 공간(사용자 언어), 스펙은 해결 공간(개발자 언어)으로 분리한다.
- 넓어짐은 개발자 관점을 앞당겨서가 아니라 범위 규율(성공 기준, non-goals, MVP 컷)로 통제한다.
- 질문 일곱 묶음:
  1. 누구의 어떤 문제 — 누가, 어떤 상황에서, 지금은 어떻게 해결하나, 어디가 아픈가
  2. 핵심 여정 하나 — happy path 하나. 여정이 둘 이상이면 MVP가 아니라는 신호
  3. 성공 기준 — 관찰 가능한 형태로
  4. 하지 않을 것 — 의도적으로 버리는 기능 목록
  5. 제품 정체성에 속하는 비싼 결정 — 계정 모델, 멀티테넌시, 과금 단위, 데이터 소유, 플랫폼. 기획에서 결정한다
  6. 제품 성격과 톤 — 디자인 테마는 여기서 사용자 언어로만(느낌·참고 제품). 구체 값(hex, 폰트)은 스펙의 토큰 레지스트리에서
  7. 기술 냄새가 나는 비싼 결정의 표시 — 풀지 않고 "스펙에서 해소할 비싼 결정" 대기 목록에 적기만 한다
- 결정 성격 구분: 제품 정체성 결정은 기획에서 결정, 기술 결정은 표시만 하고 스펙으로 넘긴다.
- 마무리 압력 방지 장치:
  - 묶음별 종료 조건 명시(예: 핵심 여정은 실패 분기 최소 하나 언급 전에는 닫을 수 없다). 사용자가 명시적으로 "넘어가자"라고 한 경우만 예외
  - blind-spot 탐침 각도 목록을 묶음마다 보유(빈 화면 첫 경험, 데이터 없는 첫날, 이탈 후 복귀, 의도와 다른 사용, 공유 받는 쪽의 경험). 닫기 전에 안 다룬 각도를 던지고 닫는다
  - 기획 문서 안에 묶음별 상태표(다룬 각도 / 안 다룬 각도 / 열린 질문)를 두고 갱신 — 디스크가 앵커
  - 탐침 강도는 가변: 답변이 얇아 보일 때만 파고든다
- 산출물: 기획 문서 + 비싼 결정 대기 목록(스펙 렌즈의 첫 입력)

### 스펙 렌즈 (개발자 관점)

1. 비싼 결정 해소 — 대기 목록 항목마다 되돌리기 비용 등급(S/M/L/XL)을 매기고, 선택과 이유를 서너 줄 기록(경량 ADR). 등급이 클수록 대안 비교 의무화. 공들임을 가역성 등급에 비례시킨다
2. 전역 레지스트리 정의 — 디자인 토큰(제품 성격을 구체 값으로 변환), 공통 컴포넌트 명단, 백엔드 공통 계층(에러 형식·인증·로깅), DB 스키마
3. 싼 결정은 의도적으로 비워두기 — 가역성 높은 결정은 "구현 재량"으로 명시. 비싼 곳만 촘촘한 스펙이 이 플러그인의 차별점
4. 강제 장치 설치 계획 — 훅·린트 규칙(하드코딩 검출, 명단 동기화 검사)을 어디에 어떻게 심을지. 실제 설치는 플랜의 phase 1에 step으로 들어가 런에서 실행된다

- 타이밍: 스펙 단계에서는 마크다운 명단까지만. 실제 코드(토큰 파일 등)는 기술 스택이 정해진 플랜/런에서 만든다.

### 전역 관리 구조

- 영역별(백엔드/DB/프론트/디자인) 레지스트리 파일을 각 영역에 두고, 해당 영역 작업 전에 먼저 읽게 한다.
- 세 원칙:
  1. 얇은 색인 — 이름, 한 줄 설명, 실제 파일 위치, 언제 쓰는지만. 내용은 복사하지 않는다(지도이지 문서가 아니다)
  2. 코드가 진실의 원천 — 디자인은 토큰 파일 자체가 레지스트리, 마크다운은 가리키기만
  3. 동기화를 기계로 검증 — 공통 폴더에 새 파일이 생겼는데 명단에 없으면 린트가 잡는다
- "먼저 읽기"도 재량에 맡기지 않고 영역별 CLAUDE.md 또는 훅으로 강제한다.

### 플랜 렌즈

- 입력: 스펙(비싼 결정 확정 + 레지스트리 명단 + 재량 표시). 출력: phase > step 구조와 step별 문제지.
- phase 분해 기준 — 가역성 순서 (**확정: 기반 먼저**):
  - phase 1은 되돌리기 비싼 기반을 실물화한다: DB 스키마, 디자인 토큰 파일, 공통 컴포넌트 최소 세트, 백엔드 공통 계층, 강제 장치(린트·훅) 설치. 스펙에서 마크다운 명단이던 레지스트리가 여기서 실제 코드가 된다
  - 근거: 비싼 결정일수록 코드가 쌓이기 전에 실물화해야 수정 비용이 가장 싸고, 이후 모든 step이 "이미 존재하는 공통 요소를 재사용"하는 상황에서 시작되어 하드코딩 유혹이 줄어든다
  - phase 2부터는 그 기반 위에 기능을 수직 슬라이스(사용자 여정 조각 단위)로 쌓는다
- step 분해 기준: 서브에이전트 하나가 한 컨텍스트 안에서 끝내고, 완료를 기계로 확인할 수 있는 단위. 애매하면 더 쪼갠다.
- 문제지(step 계약서) 여섯 항목:
  1. 목표 한 줄
  2. 수용 기준 — 관찰 가능한 문장으로
  3. 경계 테스트 — 구현 전에 확정하는, 검증자가 돌릴 테스트 목록
  4. 읽을 색인 — 이 step이 건드리는 영역의 레지스트리 지정
  5. 검증 등급 — fresh(신선한 눈 검증자) 또는 basic(린트+테스트). 건드리는 결정의 가역성 등급에서 자동으로 따라온다
  6. 재량 범위 — 스펙이 비워둔 부분 중 이 step에 해당하는 것을 명시해, 구현자가 스스로 정해도 되는 영역을 알게 한다

### 런 렌즈

- 구조: phase > step (step은 사용자가 정한 명칭). 서브에이전트 방식으로 실행.
- 서브에이전트 3층 구조:
  - 메인 세션 = 지휘자: 플랜을 읽고 step을 순서대로 배분하며 결과를 받아 넘긴다. 코드를 직접 짜지 않는다
  - 구현자 서브에이전트: step 계약서와 해당 영역 레지스트리를 들고 구현한다
  - 검증자 서브에이전트: fresh 등급 step에서 구현자와 완전히 분리된 새 컨텍스트로 뜬다. 서브에이전트 구조 덕분에 컨텍스트 격리(신선한 눈)가 자연스럽게 강제되고, 메인 컨텍스트가 가벼워 긴 런에서도 지휘자가 흐려지지 않는다
- 진행: 직렬 기본 — step 검증 통과 → 수정 → 다음 step. (병렬은 의존성이 없는 step에만 해당하며, MVP 범위에서는 직렬로 간다. 가역성 비례 검증 덕에 싼 step은 빠르게 지나가므로 직렬 비용이 크지 않다.)
- 네 규칙:
  1. 강제 장치 확인 — phase 1에 스펙 4번의 설치 step이 들어 있는지 런 시작 브리핑에서 확인하고, 빠져 있으면 추가한다
  2. 작업 전 색인 읽기
  3. 공통 요소 규칙 — 명단에 있으면 재사용, 없으면 공통 폴더에 만들고 같은 커밋에서 명단 갱신. "일단 하드코딩 후 정리" 금지
  4. 숨은 비싼 결정 에스컬레이션 — 구현 중 마주친 결정에 가역성 등급을 매겨, S/M은 결정 후 기록 한 줄, L/XL은 멈추고 보고. **확정: L/XL만 멈춤이 기본값.**
- 멈춤의 사용자 경험:
  - 런 시작 브리핑에서 "L/XL 결정을 만나면 멈춘다"를 고지하고, 플랜의 검증 등급 표시를 근거로 멈출 가능성이 있는 step들을 미리 보여준다
  - 멈출 때는 pending-decision 파일에 상황·선택지·추천안을 기록한다. 사용자가 자리를 비웠어도 돌아와서 파일 하나만 읽고 답할 수 있게
  - pending-decision 파일의 수명: 사용자가 답하면 그 내용을 결정 기록(스펙 렌즈 1번과 같은 경량 ADR 로그)으로 옮겨 적고 pending 파일은 삭제한다. 우편함은 비우고, 기록은 영구 보존한다. 재개 시점에 pending 파일이 남아 있으면 아직 답하지 않은 결정이 있다는 뜻이 되므로, 파일의 존재 자체가 상태 표시 역할을 한다
  - 푸시 알림은 하네스의 Notification 훅에 연결 가능하게 문서화한다(ntfy·텔레그램·슬랙 등 사용자 채널). 플러그인이 강제하지는 않는다
  - 실행 모드는 런 시작 브리핑에서 사용자가 선택한다: 기본값은 동반 모드(L/XL에서 멈추고 질문). 자율 모드(야간 무인 실행)를 고르면 멈추지 않는 대신 가장 가역적인 임시 선택을 하고 provisional 표시 후, L/XL 결정 모음을 보고서로 남긴다

### 검증 설계

- 신선한 눈 = 컨텍스트 격리 (모델 교체가 아니다). 맹점은 공유된 컨텍스트를 타고 전염된다.
  - 검증자에게 주는 것: step 계약서(수용 기준), diff, 실행 방법, 레지스트리 규칙
  - 주지 않는 것: 구현자의 작업 서사·자기 평가
- 문제지/채점 분리는 시점으로 해결:
  1. 문제지 = 플랜 시점 — 수용 기준과 경계 테스트를 구현 코드 존재 전에 확정
  2. 구현 = 런 시점
  3. 채점 = step 종료 시점 — 새 컨텍스트의 검증자
- 검증자 지시문은 반박 헌장("실패하는 이유를 찾아내라"). 자기만의 탐침 테스트를 새로 쓸 권한 부여.
- 세 층위: step 검증 → phase 통합 검증 → 런 전체 신선한 눈 리뷰
- 검증 밀도는 가역성 비례: 비싼 결정을 건드리는 step(스키마·공통 컴포넌트·전역 계층)은 신선한 눈 검증자 필수, 싼 step은 린트+테스트 통과로 충분. 플랜 시점에 step마다 검증 등급을 미리 표시한다.

## 구현 스케치 (제안 — 구현 세션에서 확정)

Claude Code 플러그인 형식으로, 스킬 네 개 + 공유 참조 자료로 구성한다.

```
wellbegun/
├── .claude-plugin/plugin.json
├── skills/
│   ├── begin/     # 기획 렌즈 (이름 후보: begin / discover / envision)
│   ├── spec/      # 스펙 렌즈
│   ├── plan/      # 플랜 렌즈
```

## 다음 세션 시작 가이드

1. 이 문서를 처음부터 읽는다. 확정된 결정은 "확정된 결정" 절에 전부 있다.
2. 남은 열린 질문 세 개(훅·린트 세부, 배포 형태, 스킬 이름·파일 구조)는 구현 중에 사용자와 확정한다.
3. 구현 순서 제안: 플러그인 골격 → begin 스킬 → spec 스킬 → plan 스킬 → run 스킬 → 참조 자료 → 실제 프로젝트 하나로 시식(dogfooding).
4. 이 플러그인 자체의 구현에도 이 플러그인의 철학을 적용한다: 스킬 파일 구조와 이름이 이 프로젝트의 "비싼 결정"이다(배포 후 바꾸면 사용자가 깨진다). 스킬 본문 문구는 싼 결정이다(언제든 고칠 수 있다).
