# wellbegun 0.7.4 — Goal and abuse checks for verifiers

Light changes from the kongkong comparison experiment
([results](../2026-11-05-kongkong-comparison/feedback.md)): a full wellbegun run
had more defects against `begin.md` than a plugin-free session built from the
same spec and plan. Stage verifiers checked decision wording, not the product's
promises, and nothing looked at abuse. The runtime is unchanged; the larger
question of how heavy wellrun should be is left for a separate design.

- wellspec checks the limits of the plan tier the project will actually deploy
  on when a decision picks a hosting platform, managed service or payment
  provider, and records binding limits as constraints.
- Fresh verifiers also receive `begin.md` and check whether the contract, a
  decision or the implementation breaks one of its promises. A decision can be
  followed exactly and still defeat its goal.
- Fresh verifiers probe abuse and robustness where the target holds shared
  resources, takes untrusted input or keeps connections: anonymous clients
  holding resources, message floods, dropped connections and reconnects.
- Replacing a real path with a mock, or skipping or narrowing a test, adds a
  `coverage loss` line to `deferred.md`; the next fresh verifier judges whether
  a contract clause is left unverified.
- Checks record how many tests ran; an unexplained drop fails the check.
  Verifiers may temporarily break a money, authorization or protocol guard to
  confirm a test fails. Phase integration and whole-run review look at
  screenshots of key UI states.
