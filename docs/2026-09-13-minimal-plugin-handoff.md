# 새 플러그인 실험 — 새 세션 인계

이 문서 하나를 먼저 읽고 시작한다. 기존 wellbegun 문서·스킬 전체를 읽거나
기존 pipeline으로 이 실험을 진행하는 것을 기본값으로 삼지 않는다.

## 사용자의 의도와 작업 경계

사용자는 wellbegun의 철학은 좋아하지만 사용하는 데 드는 시간과 토큰이 크다고 느낀다.
기존 경량화 구현은 정식 릴리스로 보존하고, **완전히 새로운 폴더와 세션에서 철학만
가져온 새 플러그인**을 실험하려 한다. 이름과 세부 구조는 아직 정하지 않았다.

새 세션의 작업 대상은 사용자가 연 새 폴더다. 기존 저장소
`/Users/arden/Documents/dev/wellbegun`은 필요할 때 읽는 참고 자료다.
기존 코드 복사, 사용자 프로젝트 migration, 기존 플러그인 교체, 원격 배포는
새 실험에 자동으로 포함되지 않는다. 기존 wellbegun과 동시에 비교할 수 있도록
새 플러그인 식별자를 사용한다. KBO 원본
`/Users/arden/Documents/dev/kbo-away-fans`와 다른 Herdr 세션은 건드리지 않는다.

## 가져갈 철학

1. **비싼 결정을 일찍 드러낸다.** 제품·데이터·공개 계약 등 되돌리기 어려운
   선택을 실제로 도입하거나 바꿀 때 확인한다. 기존 계약을 사용하는 것과 구분한다.
2. **구현 전에 완료 기준을 정한다.** 작은 작업에는 몇 줄이면 충분하다.
   사용자가 이미 준 기준을 별도 문서로 다시 설명하는 작업을 기본값으로 만들지 않는다.
3. **중요한 경계는 독립적으로 검증한다.** 잘못된 새 기반을 여러 소비자에
   확산하기 전에 확인한다. 자기검토를 독립 검증으로 표시하지 않는다.
4. **중단 뒤 이어갈 수 있다.** 현재 위치, 다음 행동, 막힌 이유와 필요한 근거를
   보존한다. 이미 완료한 구현을 매 재개마다 반복하지 않는다.

속도를 위해 실패·미검증을 성공으로 바꾸거나 필수 제약을 누락하는 것은 허용하지 않는다.
사용자 변경과 기존 권한을 존중하고, 필요한 선택만 묻는다.

## 새로 검증할 설계 가설 — 확정 사양 아님

"사용자를 pipeline에 넣는 대신 평소 코딩 흐름에 필요한 순간만 개입하면,
철학을 유지하면서 플러그인 자체의 추가 비용을 크게 줄일 수 있다."

출발 후보는 작은 기본 지침 하나다. 처음부터 다섯 lens, registry, 별도 runtime,
state schema, decision ledger, hook, verifier orchestration을 만들 필요는 없다.
필요성이 실제 사례에서 드러날 때 가장 작은 장치를 추가한다. 기술적 해법을
미리 Python/Markdown/특정 host로 고정하지 않는다.

작은 UI 수정의 기대 흐름은 기준 확인 → 직접 구현 → 영향 검사 → 종료다.
플러그인을 사용했다는 이유만으로 기획 문서나 추가 에이전트가 생기지 않아야 한다.
새 데이터 계약 또는 공유 기반이라면 해당 결정과 확산 경계에서 더 깊게 개입한다.

문서 0개·에이전트 0회가 모든 작업의 목표인 것은 아니다. 무엇을 막아주는지 설명할
수 없는 절차를 기본 비용으로 부과하지 않는 것이 목표다. 장기 작업의 재개 신뢰성과
작은 작업의 낮은 부담 사이의 실제 tradeoff를 실험으로 확인한다.

## 기존 버전에서 확인한 사실

wellbegun 경량화 구현은 G1 round 7, 최종 독립 검토 round 2에서 ACCEPT를 받았다.
88개 runtime/lifecycle 검사가 통과했으며 검사 입력·환경 동일성을 대조해 재사용했다.
설치본에서는 별도 임시 프로젝트로 선택 조회, basic, gate 차단, pending/재개,
archive를 smoke 검증했다. 합성 verifier identity로 실행한 smoke는 실제 agent 판단의
품질을 증명하지 않는다.

| 통제된 step 비교 | 이전 정책 | 경량화 정책 |
|---|---:|---:|
| UI 전달 문서·dispatch 합계 | 30,103 bytes | 25,189 bytes |
| 데이터 전달 문서·dispatch 합계 | 69,520 bytes | 62,202 bytes |
| UI 모델 역할 호출 | 2 | 1 |
| 데이터 모델 역할 호출 | 4 | 3 |
| UI 완료까지 | 169.642초 | 120.830초 |
| 데이터 완료까지 | 610.340초 | 378.164초 |

위 bytes는 **여러 역할에 실제 전달된 문서의 UTF-8 합계**다. 단일 packet 크기나
토큰 수가 아니다. 작은 정상 runtime packet 관측은 3,933 bytes였다.
선택 조회로 한 번의 입력은 줄었지만 총 전달량과 역할 비용이 남았다는 문제의식이다.
어느 문서가 비용의 주원인인지는 아직 새 실험에서 분해해 확인해야 한다.

기존 수치는 단일 표본, 고정 실행 순서, warm cache, 검사 재사용과 orchestration 시간을
포함한다. provider system 입력, paired token/billing 및 전체 pipeline 비용은 미측정이다.
일반적인 속도·금액 절감이나 독립 검증의 맹검 탐지율을 증명하지 않는다.
KBO baseline-identical 코드의 범위 밖 Flutter 실패 7개도 남아 있다.

## 첫 실험 제안

먼저 짧은 설계안과 최소 프로토타입으로 출발한다. 종전의 spec/plan/runtime을
다시 만드는 일부터 시작하지 않는다. 사용자가 새 세션에 주는 구체적인 지시를 우선한다.

비교 후보는 플러그인 없음 / 정식 wellbegun / 새 최소 플러그인이다.
작은 독립 수정, 새 공유 기반과 첫 소비자, 중단 후 재개라는 사례부터 시작할 수 있다.
비싼 결정이나 주입 결함은 세 후보에 같은 시작 코드와 작업 조건으로 준다.
품질 판정 기준도 실행 전에 같게 정한다.

측정 시 task 자체 비용과 플러그인이 추가한 비용을 구분한다:

- 모델에 실제 전달한 지침·작업 문서 bytes, 측정 가능한 tokens와 사용량.
- 첫 수정까지/완료까지 시간, 모델·검증 호출 수, 사용자에게 묻는 횟수.
- 관리 문서 쓰기량, 유효 검사 중복 실행, 재개 시 반복한 작업.
- 완료 기준 충족, 비싼 결정 누락, consumer 전 결함 차단, 재개 정확성.

같은 host/model/effort/환경을 사용하고, 비교 context를 분리한다.
앞선 후보의 결과를 다음 후보에 노출하지 않는다. 비교 실험에서 agent/독립 세션 사용은
그 시점의 사용자 권한과 host 정책을 따른다. 이 문서는 추가 실행을 자동 승인하지 않는다.
작은 pilot 뒤 필요할 때 반복·순서 교차를 늘린다. 대형 benchmark 기반부터 만들지 않는다.
측정할 수 없는 값은 unknown으로 남기고 bytes를 임의로 token/금액으로 환산하지 않는다.

성공은 문서가 짧아지는 것만이 아니다. 평범한 작업의 추가 부담이 작고, 중요한 경계에서는
비용을 지불할 만한 보호가 관찰되어야 한다. 보호가 무너지면 전체 기존 시스템을 되살리기
전에 어떤 최소 정보/개입이 부족했는지 확인한다. 수치 목표는 pilot 근거로 정한다.
