# wellnext — 사이클 개폐 설계

- 작성일: 2026-08-31
- 상태: 설계 확정, 구현 대기
- 배경: kbo-away-fans 1차 완주 후 2차 개발을 시작하려 했더니 파이프라인에 재진입 입구가 없음을 확인. 이 문서는 wellbegun을 1회용 MVP 파이프라인에서 n차 사이클을 지원하는 파이프라인으로 확장하는 설계를 담는다.

## 한 줄 컨셉

완주된 wellbegun 프로젝트에 새 작업 덩어리가 들어올 때, 다섯 번째 스킬 **wellnext**가 레지스트리 실사 → 진입 판정 → 사이클 개폐를 담당한다. 기존 네 스킬은 델타 모드만 배우고, 결정 장부는 supersede 표기로 역사를 보존한다.

## 왜 필요한가 (1차 완주 후 드러난 세 가지 구멍)

1. **파이프라인이 1회용이다.** 네 스킬의 가드가 전부 "전 단계 approved → 다음으로 라우팅"하는 일방통행이라, begin/spec/plan이 모두 approved이고 런까지 끝난 프로젝트에는 2차 사이클을 시작할 입구가 없다.
2. **그린필드 전제가 박혀 있다.** wellspec은 레지스트리를 "새로 정의"하고 wellplan의 phase 1은 "로스터를 실제 코드로" 만드는 고정 단계인데, 2차에서는 토큰·공용 컴포넌트·스키마·훅이 이미 코드로 존재한다.
3. **결정을 뒤집는 절차가 없다.** kbo-away-fans 1차는 "계정 없이 시작"을 정체성으로 결정하고 스탬프를 non-goal로 던졌는데, 2차 기능 목록(로그인·배지·좋아요)이 정확히 그 결정들을 뒤집는다. decisions.md에 기존 ADR을 대체하는 표기가 없다.

## 확정된 결정

### 전략

- **케이스별 진입.** 사이클마다 진입 지점(begin부터 / spec부터 / 파이프라인 불필요)을 다르게 고를 수 있다. 단, 진입 판정은 감이 아니라 규칙이 한다.
- **규칙이 제안 + 사용자 확정.** 에이전트가 두 축으로 검사해 근거와 함께 제안하고, 사용자가 확정한다. wellspec의 L/XL 확인과 같은 철학.
- **진입 기준은 두 축이다** — "정체성을 건드리나"가 아니라: ① 기존 정체성 결정·non-goal을 뒤집는가, ② 새 사용자 여정을 추가하는가. begin의 가치는 정체성만이 아니라 사용자 렌즈(여정·실패 분기·probe angle)이므로, 정체성이 무사해도 새 여정이 생길 만큼 큰 개발은 begin(델타 범위)을 통과한다.
- **다섯 번째 스킬 신설 (A안).** 개폐 로직을 한 스킬에 모은다. 가드 확장안(B안)은 로직이 네 곳에 분산되고 발동 주체가 애매해져 기각. 2차부터 별도 프로세스안(C안)은 XL급 문(계정·위치 권한·OAuth)이 몰리는 시점에 되돌림 비용 장치를 버리는 셈이라 기각.

### 사이클 상태 모델

- **최상위 `.wellbegun/*.md` = 항상 현재 사이클.** 네 스킬의 경로 참조·가드 로직이 그대로 유지되는 것이 이 선택의 핵심 장점.
- **`cycles/NN/` = 완료 사이클의 불변 보관소.** 새 사이클이 열릴 때 이전 사이클의 begin/spec/plan/run.md(+ audit.md)를 옮긴다. 보관된 문서는 그 시점의 기록이므로 이후 수정하지 않는다.
- **`decisions.md`는 아카이브하지 않는다.** 누적 장부로 최상위에 남는다. 사이클 경계마다 `## cycle N` 헤더로 구획한다.
- **디렉토리는 순번, 날짜는 frontmatter.** 사이클의 의미 있는 축은 순서이므로 이름은 `cycles/01/`. 날짜는 frontmatter가 담당한다: 시드 시 `cycle: N` + `opened: YYYY-MM-DD`, 아카이브 시 옮기는 begin.md에 `closed: YYYY-MM-DD` 스탬프(아카이브 행위의 일부이므로 불변 원칙과 충돌하지 않음). 날짜 frontmatter가 없는 1차 파일은 아카이브 시점에 git log에서 역산해 채운다.
- **하위 호환.** `cycle` frontmatter가 없는 기존 파일은 1차로 간주 — kbo-away-fans는 마이그레이션 없이 호환된다.
- **현재-정답지 원칙.** "현재 정체성이 뭐지?"를 알려고 아카이브를 거슬러 올라가게 만들지 않는다. 델타 begin의 번들 5가 "이전 결정 나열 + 뒤집기 반영"이므로, 최상위 begin.md에는 항상 현재 유효한 정체성 결정의 전체 목록이 실린다. 아카이브는 역사책, 최상위는 정답지.

### wellnext 스킬

**발동 조건 (description).** "파이프라인이 완주된 wellbegun 프로젝트에 새 작업 덩어리(기능 목록, 플로우 차트, n차 개발)가 들어올 때."

**가드.**
- `plan.md` approved + `run.md` 전 스텝 완료 → 이 스킬 적용.
- 파이프라인 진행 중 → 해당 단계 스킬로 라우팅.
- `pending/` 비어 있지 않음 → wellrun으로.

**1단계 — 레지스트리 실사 (진입 판정보다 먼저).** 전역 관리는 이 플러그인의 또 하나의 축인데, 사이클 사이에 파이프라인 밖 개발(예: 디자인 테마 작업, 핫픽스)로 로스터와 코드가 어긋났을 수 있다. 거짓말하는 장부 위에 델타 spec을 얹지 않기 위해 셋을 본다:

1. **로스터 ↔ 코드 대조 (드리프트 감지).** 네 로스터(토큰·공용 컴포넌트·백엔드 공통·스키마)를 실제 코드와 대조해, 로스터에 없는데 코드에 생긴 것 / 로스터에 있는데 코드에서 사라진 것을 찾아 로스터를 현실에 맞게 먼저 갱신한다.
2. **강제 장치 점검.** phase 1에서 설치한 훅·린터가 살아 있고 green인지, 편집 단위가 아니라 전체 코드베이스 일괄 실행으로 확인한다. 기존 훅 스크립트 재사용.
3. **중복 스캔 (승격 후보).** "2회 이상 중복이면 전역으로" 규칙의 탐지부. 반복되는 shared-shaped 패턴(하드코딩 색상값, 복제된 에러 처리·위젯 구조)을 찾아 승격 후보 목록으로 정리한다. **wellnext는 찾기만 하고 결정하지 않는다** — 등급을 매겨 레지스트리에 넣을지 정하는 것은 개발자 렌즈의 일이므로, 목록은 wellspec 델타 모드 step 2의 입력으로 넘긴다. 렌즈 분리: wellnext는 탐색·판정·개폐, wellspec은 결정.

실사 결과는 `.wellbegun/audit.md`로 남겨 현재 사이클과 함께 굴러가다 사이클 종료 시 같이 아카이브된다.

**2단계 — 진입 판정 (triage).** 새 작업 내용, 이전 begin.md(정체성·non-goals), decisions.md, 실사 결과를 대조해 두 축으로 검사하고, 세 판정 중 하나를 근거와 함께 제안한다:

| 판정 | 조건 |
|---|---|
| begin 진입 (델타 begin) | 정체성·non-goal을 뒤집거나, 새 사용자 여정을 추가 |
| spec 진입 | 둘 다 아니고 기존 여정 위의 확장 |
| 파이프라인 불필요 | 파이프라인이 과할 정도로 작은 수정 — 훅이 지키는 채로 그냥 작업 |

실사 결과가 판정 근거에 들어간다: 새 기능이 기존 공용 요소로 얼마나 커버되는지 알면 "기존 여정 위 확장" 여부를 더 정확히 가릴 수 있다. 사용자 확정 후에만 다음 단계로.

**3단계 — 개시 절차 (확정 후).**
1. `cycles/NN/` 생성, 이전 사이클 문서 이동(+ closed 날짜 스탬프). decisions.md는 남기고 `## cycle N` 헤더 추가.
2. 새 사이클 문서 시드: frontmatter에 `cycle: N`, `entry: begin|spec`, `opened` 기록. **spec 진입이어도 얇은 begin.md를 자동 생성한다** — 이전 begin의 상속 선언 + 이번 델타 여정 요약을 담고, 진입 확정 자체가 승인이므로 `status: approved`로 시작. 이로써 wellspec의 기존 가드("begin 없으면 wellbegin으로")가 수정 없이 통과되고, begin을 건너뛴 사이클이 상류 문서를 낡게 만드는 문제도 막는다.
3. 확정된 진입 렌즈 호출.

### 델타 모드 (기존 네 스킬의 변경)

공통 스위치: 현재 사이클 문서의 frontmatter `cycle: N`(N > 1)을 보고 델타 모드로 동작. 1차 프로젝트에서는 기존과 완전히 동일 — 기존 동작을 깨지 않는다.

- **wellbegin.** 번들 5(정체성)는 "이전 사이클 결정 나열 + 이번에 뒤집는 것만 논의"로 축약. 번들 1(whose problem)도 대개 상속 확인. 번들 2·3·4(여정·성공 기준·non-goal)는 새 기능 대상으로 정상 밀도 진행 — 새 여정의 분기 질문(예: 배지의 "잠실 교차 찍기")이 여기서 잡혀야 한다. probe angle 점검 동일 적용.
- **wellspec.** step 2 분기: 레지스트리를 새로 정의하는 대신 코드로 존재하는 기존 레지스트리를 먼저 읽고 **확장분 로스터만** 작성. wellnext 실사의 승격 후보 목록이 추가 입력. step 1(큐 해소)은 동일하되, 그레이딩 때 decisions.md의 기존 ADR과 충돌하는지 확인하는 절차 추가 — 충돌 시 supersede.
- **wellplan.** phase 1이 "델타 파운데이션": 새 기반 요소(예: users 마이그레이션, 팀 컬러 토큰, 인증 공용 레이어)의 실체화와 로스터·훅·CLAUDE.md 갱신만. 기존 파운데이션 재작성은 금지 항목으로 명시.
- **wellrun.** 변경 거의 없음. 1차가 남긴 회귀 스위트와 커밋된 probe들이 컨덕터의 회귀 실행 기반으로 그대로 활용된다. run.md는 사이클마다 새 파일.

### decisions.md — supersede 표기

결정을 뒤집을 때는 새 ADR 라인에 `supersedes: <날짜> <슬러그>`를 달고, 뒤집힌 옛 라인 끝에 `(superseded <날짜>)`를 마킹한다. 옛 기록은 지우지 않는다 — "왜 그때는 그렇게 갔나"가 다음 뒤집기의 판단 재료다.

```markdown
- 2026-08-24 계정 모델: 계정 없이 시작. 이유: MVP 검증에 집중 … (superseded 2026-09-01)
- 2026-09-01 계정 모델: 이메일+구글+카카오 로그인 도입. supersedes: 2026-08-24 계정-모델.
  이유: 배지·좋아요가 기기 저장으로는 불가능해짐 …
```

정체성·non-goal을 뒤집는 사이클은 supersede ADR 기록이 의무이고, 현재 사이클 begin.md에도 반영되어야 한다(현재-정답지 원칙).

또한 등급 희석 대책(2026-08-28 결정, kbo-away-fans에서 실물 적용 완료)을 정식 규칙으로 승격한다: decisions.md는 상단에 **L/XL 색인 섹션**을 두고, 원장은 `## 원장 (시간순 추가 전용)` 헤더 아래에 둔다. 색인은 supersede가 일어날 때 함께 갱신한다 — 색인에는 현재 유효한 L/XL만 남긴다.

### 중간 개발과의 공존

- **훅 = 실시간 방어, 실사 = 사이클 개시 시 정산.** 전역 관리의 강제 장치(훅·린터·영역 CLAUDE.md)는 스킬이 아니라 리포에 설치된 인프라이므로 파이프라인 밖 개발 중에도 작동한다. 훅이 못 잡는 것(로스터 갱신 누락, 중복 누적)은 다음 wellnext 실사가 정산한다.
- **리듬.** 완주 → (자유 개발: 버그픽스·소수정은 wellnext 없이) → 덩어리 작업이 오면 wellnext → 사이클 N → 완주 → 반복.

### 문서 갱신 범위

- 네 스킬의 description을 사이클 인지형으로 수정 — 특히 wellbegin의 "before any spec, plan, or code exists"는 델타 begin을 막는 문구.
- README의 파이프라인 설명에 wellnext와 사이클 개념 추가.
- 스킬 본문·description은 기존 관례대로 영어, 설계 문서는 한국어.

## 구현 범위 밖 (이번에 안 하는 것)

- 중복 스캔의 자동화 도구(전용 스크립트) — 첫 구현은 스킬 지시문 + 기존 훅 스크립트 일괄 실행으로 충분. 패턴이 잡히면 도구화 검토.
- 사이클 간 diff 리포트, 사이클 목록 대시보드 — 필요가 증명되기 전에는 만들지 않는다.
- kbo-away-fans의 1차 파일 선제 마이그레이션 — 하위 호환 규칙(cycle 없음 = 1차)으로 대체.
