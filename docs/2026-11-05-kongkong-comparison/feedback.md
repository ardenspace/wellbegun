## 해석
1. **설계 단계(begin·spec·plan)는 가치가 있었다 (B vs C).** spec·plan을 받은 B는 배포할 수 있는 구조, 서버 쪽 결제 확인과 웹훅, 비용표, 꽉 참 분기까지 갖췄다. begin만 받은 C는 여정은 잘 만들었지만 출시하려면 구조를 새로 짜야 한다. 걸린 시간은 비슷했다.
2. **실행 단계(wellrun)는 이번에 결과를 더 좋게 만들지 못했다 (A vs B).** 같은 설계 문서에서 출발했는데, begin 기준 평가에서 A가 B보다 결함이 많았다. 테스트는 A가 두 배였다. 비용은 A가 훨씬 컸다.
   - 로비 shard 결함은 phase-3 fresh 검증을 통과했다. 결정(dec-0021) 문구는 지켰지만 begin.md의 약속을 어겼다. B는 같은 충돌을 스스로 발견해서 shard를 1로 두었다.
   - 간헐 실패를 고치려고 e2e에서 실제 소켓을 가짜로 바꾼 결정(dec-0025)이 실제 worker를 거치는 돈 흐름의 자동 확인을 없앴다. 아무 verifier도 지적하지 않았다.
   - "돌아온 사람에게 내 꾸미기가 안 보임", "환불 미처리", "친구가 누구인지 표시 안 됨"은 단계 계약에 없는 begin 수준의 약속이라 단계 verifier가 보지 않았다.
3. **세 결과물 모두 놓친 것: 로그인 없는 사용자가 자원을 붙잡는 경우.** 빈 소켓, 로비 배정 반복 호출, 링크의 콩콩이장 채우기. 계약과 검증 어디에도 악용 관점이 없었다.
4. **마지막에 한 번 하는 독립 리뷰가 효과가 컸다.** B와 C 모두 마지막 리뷰에서 가장 심각한 결함(open redirect, 서버를 죽이는 입력, 성공 지표 부풀림)을 잡았다. 두 세션 모두 "더 이른 시점(프로토콜을 만든 직후)에 리뷰했으면 좋았겠다"고 적었다.

## wellbegun에 제안
1. **설계 단계는 유지한다.** 특히 spec의 배포 플랫폼, 서버 권한, 비용 결정이 출시 준비에 결정적이었다. 다만 "배포할 플랜의 제약"(예: Free 플랜은 SQLite DO만)을 spec에서 확인하게 한다 (B가 whole-run에서야 발견).
2. **wellrun을 가볍게 한다.** 기본은 한 세션 안에서 구현하고, 독립 검토는 위험 지점(돈·인증·공용 프로토콜을 처음 만든 직후)과 마지막에만 둔다. 지금처럼 step·gate·phase마다 fresh verifier를 돌리는 것은 비용 대비 효과가 낮았다.
3. **verifier에게 begin.md를 함께 주고, "결정이 목표와 충돌하는가"를 묻는다.** 결정 문구만 보면 로비 shard 같은 결함이 통과한다.
4. **검토 관점에 악용·견고성을 넣는다.** 익명 사용자가 자원을 붙잡거나 메시지를 쏟아붓는 경우, 끊긴 연결, 재접속.
5. **테스트 범위가 줄어드는 변경을 잡는다.** 실제 경로를 mock으로 바꾸는 수정은 "무엇의 자동 확인이 사라지는가"를 기록하고 verifier가 판단하게 한다.
6. **두 세션이 공통으로 원한 장치:** 기대한 테스트가 실제로 돌았는지 개수로 확인(B: 모바일 e2e가 조용히 빠짐), mutation 확인 체크리스트, 스크린샷을 보고 이상한 점을 찾는 단계(둘 다 테스트가 통과한 상태에서 화면 결함을 눈으로 잡음).
7. **상태 관리 비용을 줄인다.** context id 규칙, drift·cascade, 공용 파일 하나 수정이 검증 기록 여러 개를 무효로 만드는 문제(디버그 표시 하나에 verifier 2회, recheck 4회)가 실제 결함 찾기보다 시간을 많이 썼다.
